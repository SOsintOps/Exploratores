Customising Exploratores Pages

Project Structure and Standards

This section outlines the fundamental organization of the toolkit's files and pages, ensuring consistency and maintainability.

Directory Structure

The project is organized into a simple and clear directory structure to separate content from assets.

Exploratores/
├── assets/
│   ├── css/
│   │   └── style.css
│   ├── js/
│   │   ├── main.js
│   │   ├── search-library.js
│   │   └── config.js
│   └── images/
│       └── roman-helmet.ico
├── pages/
│   ├── Names.html
│   ├── Searchengines.html
│   └── ... (all other tool pages)
└── launchme.html
  • assets/: Contains all shared resources. This includes the single CSS file, all centralized JavaScript files, and all images like the favicon.
  • pages/: Contains all the individual HTML files that make up the toolkit's tools and content pages.
  • launchme.html: The main entry point or index page of the toolkit, located at the project root.

Standard Page Organization

Every HTML page in the pages/ directory must follow a standard block structure to maintain consistency and ensure all scripts function correctly.

  1. <head>: The head section must contain all standard metadata, including charset, viewport, a descriptive title, and links to the Google Fonts file, the main `style.css` file, and the site's favicon.
  2. <nav>: The main navigation bar, which must be identical across all pages. The only difference should be the presence of the class="active" on the link corresponding to the current page.
  3. <main>: This tag contains the primary, unique content for the page. All forms, inputs, buttons, and text specific to the page's function reside here.
  4. <footer>: The standard site footer, which should also be identical across all pages.
  5. <script> includes: At the very end of the body, before the closing </body> tag, links to the centralized JavaScript files are placed. This is followed by an optional page-specific script block if the page has interactive elements.

Centralized CSS File: `style.css`

All visual styling for the entire toolkit is controlled by the single file located at assets/css/style.css. This approach ensures a consistent look and feel, and makes site-wide visual changes (like modifying the color theme) easy to implement by editing just one file. No inline style="..." attributes or page-specific <style> blocks should be used. The file is organized with clear comment blocks (e.g., `/* NAVBAR */`, `/* BUTTONS */`) and uses CSS variables (defined in :root) for theming.

JavaScript Architecture in Detail

The toolkit's logic is primarily handled by two centralized JavaScript files, which work together with a small, page-specific script.

1. `assets/js/search-library.js` (The "Catalog")

This file's only purpose is to act as a central database of search configurations. It contains a single large object, SearchLibrary, which maps a search ID to a "recipe" for how to perform that search. It contains the "what" of a search, not the "how".

Anatomy of a Configuration Entry:

'names-us-radaris': { 
  urlTemplate: 'https://radaris.com/p/{firstName_RAW}/{lastName_RAW}',
  validator: 'getAndValidateName' 
},
'names-interpol': {
  urlTemplate: 'https://www.interpol.int/en/How-we-work/Notices/View-Red-Notices',
  no_input: true
}
  • Key (e.g., 'names-us-radaris'): A unique string that must match the data-search-id on a button in the HTML.
  • urlTemplate: The destination URL. Values in curly braces {...} are placeholders that will be replaced with user input. The suffix _RAW (e.g., {firstName_RAW}) is a special flag that tells the engine *not* to URL-encode the value.
  • validator: The name (as a string) of the validation function that must exist on the specific HTML page. This function is responsible for gathering and validating the inputs for this search.
  • no_input: An optional property. If set to true, the button will be active immediately and will simply open the urlTemplate link without requiring any user input.

2. `assets/js/main.js` (The "Engine")

This file contains the core, reusable logic that powers every page. It initializes common features and handles all search events. It contains the "how" of the application.

Key Functions within the Exploratores object:

  • init(): The main entry point called when a page loads. It orchestrates the other initialization functions.
  • initNavbar(): Attaches the necessary event listeners to the main navigation menu to handle the dropdown hover effect.
  • initLightMode(): Reads the config.js file and applies the .hidden-in-light class to any elements listed in the selectorsToHide array.
  • initSearchHandler(): This is the most important function. It attaches a single click listener to the page and performs a series of steps to handle search button clicks based on the data-driven architecture.

Adding a New Search Button

To add a new search tool to an existing page, you must modify the search library and add the button to the HTML, without writing a new JavaScript function for each button.

  1. Step 1: Add a Configuration to `search-library.js`

    Open the file assets/js/search-library.js and add a new entry to the SearchLibrary object. This entry is the "recipe" for your search, defining its unique ID, its target URL with placeholders, and the name of the function that will validate its input.

  2. Step 2: Add the Button to the HTML Page

    In your HTML page, place the button in a .button-grid. The button must have a unique `id` attribute (for the hide/show system) and a `data-search-id` attribute that exactly matches the key you created in `search-library.js`.

  3. Step 3: Ensure a Validator Function Exists

    In the page-specific script at the bottom of the HTML file, ensure the validation function named in the library exists. This function is responsible for reading the values from the page's input fields, checking if they are valid, and returning an object of parts for the URL template.

Creating a New Tool Page from Scratch

This guide outlines the complete process for building a new, fully functional tool page that integrates correctly with the project's architecture.

  1. Step 1: Create the HTML File

    The easiest method is to duplicate an existing tool page (e.g., `Names.html`) in the pages/ directory and rename it. This ensures the new file already contains the correct document structure, head content, nav, footer, and script includes. Immediately open the new file and update the <title> tag and the main <h1> to reflect the new page's purpose.

  2. Step 2: Define the Page's HTML Structure

    Inside the <main> tag, remove the old content and build the new interface. Use the project's standard CSS classes (.columns, .search-instructions, .button-grid) to maintain visual consistency. Assign a unique id to every input field, button, section, or column that may need to be configured by the `hidden-in-light` system. All buttons must have a `data-search-id` attribute.

  3. Step 3: Add New Configurations to `search-library.js`

    For each new search button you added in the HTML, create a corresponding entry in the `SearchLibrary` object within `assets/js/search-library.js`. Define its `urlTemplate` and specify the name of the validation function that will be used on this new page (e.g., validator: 'getAndValidateNewPageInput').

  4. Step 4: Write the Page-Specific JavaScript

    At the bottom of your new HTML file, write the necessary page-specific script. This must include: the validation function(s) you named in the library, the `updatePageState` function to manage live feedback and button states, and the `setInitialPageState` function to ensure the page loads correctly. Finally, add the `DOMContentLoaded` listener to wire up the events for your page's inputs.

  5. Step 5: Update the Navigation Bar

    This is a critical manual step. You must edit **every other existing HTML file** to add the link to your new page in the appropriate `<nav>` submenu. Forgetting this step will make your new page an "orphan" that cannot be reached from the rest of the toolkit.

  6. Step 6: Test Thoroughly

    Open your new page in a browser. Open the Developer Console (F12) and check for any errors. Test the input validation, ensure buttons enable and disable correctly, and verify that each button click opens the correct, fully-formed URL in a new tab.
