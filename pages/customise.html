Customising Exploratores Pages

Page Structure Overview

Exploratores OSINT Toolkit pages follow a consistent HTML structure to ensure maintainability and a uniform user experience. All styling is handled by an external CSS file linked in the <head>.

Key HTML Components:

  • <!DOCTYPE html> and <html lang="en">: Standard document declaration.
  • <head>: Contains:
    • <meta charset="UTF-8" />
    • <meta name="viewport" content="width=device-width, initial-scale=1.0"/>
    • <title>Page Name • Exploratores</title> (Replace "Page Name" accordingly).
    • Link to Google Fonts (IBM Plex Sans).
    • Link to the external stylesheet: <link rel="stylesheet" href="../assets/css/style.css"> (path may vary based on page location).
  • <body>: Contains the visible page content, structured into:
    • <nav>...</nav>: The main navigation bar.
    • <main>...</main>: The primary content of the page.
    • <footer>...</footer>: The page footer.
    • <script>...</script>: A single block for JavaScript before the closing </body> tag.

Navbar (<nav>) Structure:

The navigation bar uses a specific nested list structure:

<ul class="menu">
  <li>
    <span>MENU TITLE</span> 
    <!-- or <a href="...">MENU TITLE</a> if it's a direct link -->
    <ul class="submenu">
      <li><a href="page.html">Submenu Item</a></li>
      <li><a href="currentpage.html" class="active">Active Submenu Item</a></li>
    </ul>
  </li>
  <!-- More LIs for other menu items -->
</ul>

The class="active" should be on the <a> tag of the current page.

Main Content (<main>) Structure:

The <main> section typically starts with:

  • <h1 class="page-title">Page Title</h1>

It then uses various semantic elements and global CSS classes for layout and styling, such as:

  • <div class="columns"> and <div class="column">: For creating multi-column layouts.
  • <section class="search-instructions">: Wraps primary input areas. Often contains a <label>, input fields, and sometimes a <div class="note">.
  • <div class="input-container">: Groups one or more input fields.
  • <div class="input-button-line">: For aligning a single input field and a button on the same line.
  • <input type="text" class="input-field">: Standard text input.
  • <div class="button-grid">: For creating responsive grids of buttons. Specific column counts can be forced (e.g., button-grid-3col).
  • <button type="button" class="button">Button Text</button>: Standard button.
  • <div class="note"><strong>NOTE:</strong> Text...</div>: For advisory notes.
  • Category titles within <main> usually use <h2>.

Footer (<footer>) Structure:

The footer has a standard text format:

<footer>
  <p>Exploratores 2.5 prototype <a href="path/to/license.html">License</a></p>
</footer>

Adapt the path to license.html as needed.

JavaScript:

All custom JavaScript for the page, including event handlers and helper functions, resides in a single <script> block placed just before the closing </body> tag. This includes the standard navbar submenu script.

Adding a New Input Field

To add a new input field to a page, follow these steps:

  1. Locate the Target Area: Decide where the new input field should appear. This is often within an existing <section class="search-instructions"> or a new one if it's for a distinct tool. You might also place it within a <div class="column"> if using a columnar layout.
  2. Add HTML for the Input Field:

    Use a structure similar to this, adapting as necessary:

    <!-- Example within a search-instructions section -->
<section class="search-instructions">
  <label for="newInputId">Your New Input Label:</label>
  <div class="input-container">
    <input type="text" id="newInputId" class="input-field" placeholder="Enter data here">
  </div>
  <!-- Optionally, add a note related to this input -->
  <div class="note"><strong>NOTE:</strong> Specific instructions for this input.</div>
</section>
    • Ensure the <label>'s for attribute matches the <input>'s id attribute.
    • Use a **unique id** for your new input field. This ID will be used by JavaScript to retrieve its value.
    • Use the class input-field for consistent styling.
  3. Consider Grouping: If the input field is part of a line with a button, use <div class="input-button-line"> to group them. 
    <div class="input-button-line">
  <label for="newInputWithButton" class="sr-only">Input:</label> <!-- Screen-reader only label if context is clear -->
  <input type="text" id="newInputWithButton" class="input-field" placeholder="Enter data">
  <button type="button" class="button" onclick="PageName_ProcessNewInput()">Process</button>
</div>

Adding a New Function with a Button

To add a new tool or functionality triggered by a button:

  1. Add the HTML Button:
    • Place the button in an appropriate location, often within a <div class="button-grid"> for a collection of tools, or a <div class="input-button-line"> if it's paired with an input.
    • Use the standard button markup: 
      <button type="button" class="button" onclick="PageName_YourNewFunction()">New Tool Button</button>
    • Replace PageName_YourNewFunction with the actual name of your JavaScript function, following the PageName_ActionDescription convention.
    • Replace "New Tool Button" with the desired button text.
    • Ensure buttons within a button-grid are alphabetized by their label if it makes sense for the group.
  2. Write the JavaScript Function:
    • Add your new JavaScript function within the single <script> block at the end of the page.
    • Follow this general structure: 
      function PageName_YourNewFunction() {
  // 1. Get and validate input value(s)
  // Example: using a helper function (you might need to create or adapt one)
  const inputValue = PageName_GetAndValidateInput('yourInputId', 'descriptive name for alert');
  
  // If validation fails (e.g., input is empty), the helper might return null or an alert might be shown.
  if (!inputValue) {
    return; // Stop execution if input is not valid
  }

  // 2. (Optional) Process the input value if needed
  // const processedValue = inputValue.toLowerCase(); // Example processing

  // 3. Construct the target URL
  const baseUrl = "https://targetservice.com/search?query=";
  // Always URI encode parameters taken from user input
  const targetUrl = baseUrl + encodeURIComponent(inputValue); 

  // 4. Open the URL in a new tab
  window.open(targetUrl, '_blank');
}
    • **Key JavaScript Practices:**
      • **Function Naming:** Use the PageName_ActionDescription convention (e.g., Domains_SearchWhois, Usernames_CheckAvailability).
      • **Input Retrieval:** Use document.getElementById('yourInputId').value to get input values.
      • **Input Trimming:** Always use .trim() on input values to remove leading/trailing whitespace: value.trim().
      • **Input Validation:** Check if essential input fields are empty. Provide an alert() to the user if input is missing. Consider creating a helper function for this, for example: 
        function PageName_GetAndValidateInput(inputId, fieldDescriptionForAlert) {
  const inputElement = document.getElementById(inputId);
  if (!inputElement) {
    // This should not happen if IDs are correct
    alert("Error: Input field '" + inputId + "' not found.");
    return null;
  }
  const value = inputElement.value.trim();
  if (!value) {
    alert("Please enter " + fieldDescriptionForAlert + ".");
    return null;
  }
  return value;
}
      • **URL Encoding:** Always use encodeURIComponent() for any user-provided values that are inserted into URL query parameters or path segments to prevent errors or security issues.
      • **Opening Links:** Use window.open(url, '_blank') to open links in a new browser tab.

        Customising Exploratores Pages

        This page serves as the technical documentation for understanding, modifying, and extending the Exploratores toolkit.

        Project Architecture

        The toolkit is built on three fundamental principles: a Data-Driven Design, Centralized Logic, and a clear Separation of Concerns.

        Directory and File Structure

        The file organization is designed to separate content (HTML pages) from shared resources (assets), ensuring order and ease of maintenance.

        Exploratores/
├── assets/
│   ├── css/
│   │   └── style.css
│   ├── js/
│   │   ├── config.js
│   │   ├── search-library.js
│   │   ├── validators.js
│   │   ├── main.js
│   │   └── externaeven.js
│   └── images/
│       └── roman-helmet.ico
├── pages/
│   ├── address.html
│   ├── communities.html
│   └── ... (all other tool pages)
└── launchme.html
        • assets/css/style.css: The single stylesheet. It controls the appearance of the entire project.
        • assets/js/: Contains all centralized JavaScript files, each with a specific role.
        • assets/images/: Contains images, such as the favicon.
        • pages/: Contains all the HTML files that constitute the tools themselves.
        • launchme.html: The toolkit's startup page.

        The Role of the Main JavaScript Files

        The JavaScript architecture is the heart of the project. Here is the role of each file.

        1. `config.js` - The Settings

        Role: This file holds global configuration data and flags, available to all pages. It is the first script to be loaded.

        • exploratoresConfig: An object containing options like `lightVersionEnabled` to activate the "light" mode and `selectorsToHide` to specify which elements to hide.
        • Global Constants: This is the ideal place for shared data, such as the `italianProvinces` constant containing the list of Italian provinces.

        2. `search-library.js` - The Catalog

        Role: Acts as a database for all search functions in the toolkit. It contains a single large object, `SearchLibrary`, which defines the "what," not the "how."

        Each entry in this file is a complete "recipe" for a search, associated with a unique `data-search-id` found on an HTML button.

        3. `validators.js` - The Rulebook

        Role: Contains the `ExploratoresValidators` object, a library of reusable functions for input validation. These functions are called by the main engine to check that the user has entered valid data before launching a search.

        4. `main.js` - The Engine

        Role: Contains the executive logic (`Exploratores.initSearchHandler`). This script is the "engine" that makes everything work. It listens for clicks on any search button, consults the "catalog" (`search-library.js`), applies the "rules" (`validators.js`), and, if everything is valid, executes the search.

        The following guides show with practical examples how to modify and extend the toolkit.

        Example A: Adding a New Search Function

        Scenario: We want to add a button to the `x.html` page to search for a user's profile on `threads.net`.

        1. Step 1: Analyze the Validator (in `validators.js`)
          The search requires a simple non-empty username. We can reuse the existing `getAndValidateUsername` validator already in `validators.js`. No new validation code is needed.
        2. Step 2: Add the Configuration to `search-library.js`
          Open `assets/js/search-library.js` and add a new entry for our search. The `search-id` will be `x-account-threads`.

'x-account-threads': {
    name: 'Threads: Profile',
    description: 'Searches for a user profile on Threads.net.',
    urlTemplate: 'https://www.threads.net/@{term}',
    validator: 'getAndValidateUsername',
    targetInput: 'input-x-account'
},
        3. Step 3: Add the Button to `x.html`
          Open `pages/x.html` and add the new button inside the `.button-grid` of the "Account & Basic Searches" section.
